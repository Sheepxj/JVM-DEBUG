## 1. 本课的目标

第一课定位计算热点，本课观察对象创建和回收。要回答：为什么堆使用量不一定一直增长，程序却可能频繁 GC？分配速率、堆占用和业务耗时之间有什么关系？

本轮使用 GC 日志、程序内分配统计和 `jstat`，不必先掌握全部 GC 算法，也不开启 JFR。暂不运行优化版或修改堆大小。

## 2. 问题代码

模拟一项数据处理任务：每次处理 8 块数据，每块为 32 KiB。程序填充缓冲区并计算校验值，多个工作线程持续执行任务。

复用 [Workloads.java](../../src/main/java/lab/Workloads.java) 的 `AllocationWorker`。下面是问题版的等价片段，省略模式选择：

```java
private static final int SIZE = 32 * 1024;
private volatile byte[] published;

public long execute(long sequence) {
    long checksum = 0;
    for (int i = 0; i < 8; i++) {
        byte[] buffer = new byte[SIZE];
        Arrays.fill(buffer, (byte) (sequence + i));
        published = buffer;
        checksum += buffer[(int) ((sequence + i) & (SIZE - 1))];
    }
    return checksum;
}
```

每项任务创建 8 个数组，有效载荷为 `8 × 32 KiB = 256 KiB`，实际分配还包括数组对象头与对齐开销。

`published` 是实验辅助字段，让数组引用被发布，以降低分配被 JIT 消除的可能。它只保留最近一次数组引用；被替换的旧数组在没有其他引用后便有机会被回收。它没有将全部历史数组持续保存下来。

先观察 `new byte[SIZE]` 与运行表现的关系，暂不阅读 `fixed` 分支。

## 4. 窗口 B：使用 jstat 观察 GC 计数

在程序仍运行时打开第二个 PowerShell：

```powershell
$Jdk = 'J:\JDK\jdk_21\temurin-21.0.12.1'
$JavaPid = 12345  # 替换成窗口 A 本次 PID
& "$Jdk\bin\jstat.exe" -gcutil $JavaPid 1000 8
```

每隔 1000 毫秒采样一次，共 8 次。字段含义以当前 JDK 输出为准，先关注：

| 字段 | 含义与观察点 |
|---|---|
| `YGC` | 年轻代 GC 累计次数，观察相邻样本间增加多少 |
| `YGCT` | 年轻代 GC 累计统计时间，单位为秒 |
| `FGC` | Full GC 累计次数；频繁年轻代 GC 不要求同时出现 Full GC |
| `E` | Eden 当前容量的使用百分比，可能随分配、回收和容量调整变化 |
| `O` | 老年代当前容量的使用百分比，结合多次观测与日志理解 |

这些累计值从 JVM 启动起统计，包含预热；程序 `RESULT` 的 GC 差值只覆盖测量阶段。二者不能直接当作相同统计窗口。G1 会调整区域划分，仅凭一次百分比不能判断泄漏。

命令与字段见 [JDK 21 jstat 官方文档](https://docs.oracle.com/en/java/javase/21/docs/specs/man/jstat.html)。

## 5. 结束后阅读 GC 日志

将下面占位文字替换为窗口 A 的实际 `Artifacts:` 完整目录：

```powershell
$Run = '这里替换为本次 Artifacts 的完整路径'

Get-ChildItem -LiteralPath $Run -Filter 'gc.log*' -File |
    Select-String -Pattern 'Pause (Young|Full).*->' |
    Select-Object -First 8
```

脚本会轮转日志，因此一起搜索 `gc.log` 和归档。匹配包含回收前后容量的暂停完成行，避免将开始行和结束行当作两次 GC；这些结果只用于阅读，不据此计算总次数。

助手短测中实际出现过如下片段，仅示范读法，不作为学习者数据：

```text
GC(2) Pause Young (Normal) (G1 Evacuation Pause) 75M->1M(128M) 2.270ms
```

- `GC(2)`：该次 GC 的事件标识。
- `Pause Young`：年轻代回收暂停，包含应用线程暂停阶段。
- `75M->1M(128M)`：本次 GC 前后整个堆的使用量约从 75 MiB 降到 1 MiB，括号中是当时堆容量。
- `2.270ms`：该条日志记录的暂停时长。

如果反复回收后堆占用明显下降，说明有许多对象可以被回收，不能据此判断内存泄漏。也不能把“GC 较多”直接等同于“GC 问题严重”，需要结合暂停、吞吐和延迟评估。

G1 日志的诊断用途见 [官方调优文档](https://docs.oracle.com/en/java/javase/21/gctuning/garbage-first-garbage-collector-tuning.html)。

## 6. 查看分配量与业务指标

```powershell
Import-Csv -LiteralPath "$Run\summary.csv" |
    Select-Object ops_per_s,p99_us,worker_alloc_mib_s,worker_alloc_bytes_per_op,gc_count,gc_time_ms |
    Format-List
```

| 指标 | 含义 |
|---|---|
| `workerAlloc` / `worker_alloc_mib_s` | 工作线程每秒分配的内存；不是每秒泄漏量 |
| `worker_alloc_bytes_per_op` | 每任务分配字节数，用来验证代码是否减少了分配 |
| `gcCount` / `gc_count` | 测量阶段 GC 计数的累计差值 |
| `gcTime` / `gc_time_ms` | MXBean 提供的累计 GC 时间差值，用于辅助观察，不当作精确全部 STW 暂停总时长 |
| `throughput` / `ops_per_s` | 每秒完成任务数 |
| `p99` / `p99_us` | 内部任务耗时直方图的 P99 估计上界，不是 HTTP 请求延迟 |

分配量是流量，堆占用是某一时刻的存量。128 MiB 堆可以通过不断分配、回收，在一秒内累计分配远超 128 MiB 的对象。

对比代码时不能只看每秒分配量，因为完成任务越多，每秒分配也可能越多；每任务分配量更能直接反映单项任务的分配行为。

## 8. 本次基线说明了什么？

已核对学习者问题版：每任务分配 262,272 字节，每秒分配约 8.409 GiB，60.012816 秒内 GC 计数增加 7,111，吞吐约 34,426 任务/秒，P99 约 1.049 毫秒。完整数据见 [实验记录](../../JVM调优实验记录.md)。

`jstat` 的 8 个样本跨约 7 秒，年轻代 GC 次数增加 879；日志反复显示 `76M->1M(128M)`，而 Full GC 计数为 0。这支持大量短命对象被频繁回收的判断。

堆无需全部占满才触发年轻代回收。可回收对象多也不意味着回收没有代价：暂停打断业务执行，GC、分配及数组初始化都消耗资源。P99 与 GC 暂停量级接近，但不能据此断定全部尾延迟来自 GC。

## 9. 优化代码：每线程复用缓冲区

问题版在循环内 `new byte[SIZE]`；现有优化版将数组放到每个 `AllocationWorker` 的初始化阶段，后续重复使用：

```java
// 初始化阶段；本实验每个工作线程独占一个 Worker。
this.reusable = fixed ? new byte[SIZE] : null;

// 每次任务的循环里，fixed 模式使用该线程自己的数组。
byte[] buffer = fixed ? reusable : new byte[SIZE];
```

填充、校验逻辑仍然执行，只改变数组创建和复用方式。这样每项任务不再重复创建 8 个数组。前提是旧内容没有被异步消费者或调用方继续使用，且数组不被工作线程并发共享。

执行第一项对比，保持 128 MiB 堆：

```powershell
Set-Location 'D:\Files\Documents\ChatGPT\JVM调优学习'
$Jdk = 'J:\JDK\jdk_21\temurin-21.0.12.1'
.\scripts\run.ps1 -JdkHome $Jdk -Scenario allocation -Mode fixed -Threads 4 -HeapMiB 128 -Seconds 60
```

预测：每任务分配大幅下降，GC 压力降低。具体吞吐、P99 和 CPU 变化以实测为准。优先看每任务分配，再比较业务指标。

### 代码优化的含义

吞吐本轮达到约 19.26 倍，P99 降低约 98.9%。每线程复用缓冲区，让每任务分配降至显示精度下近零，测量窗口没有观测到 GC。

缓冲区仍在初始化时分配；近零统计只针对工作线程的测量窗口。改动同时影响对象分配、内存复用和 GC，不能把全部加速归因于减少 GC 暂停。CPU 总占用仍可能较高，应结合完成量和每任务成本解释。

### 增大堆的含义

每任务分配保持 262,272 字节，说明代码行为未改变。本轮 GC 次数约减半，P99 降低约 64.8%，而吞吐仅高约 1.6%。更多空间改变了回收节奏，仍然需要处理持续产生的大量临时对象。

增大堆并非没有收益，但应按吞吐、延迟、内存预算等目标评估；更少的 GC 不自动意味着所有性能指标都会明显改善。

## 12. 面试复习与测量边界

本课应掌握：

1. 分配量是流量，堆占用是存量；高分配速率不等于泄漏。
2. 用 jstat 看统计趋势，用 GC 日志看回收类型、前后堆占用和暂停。
3. 对象可回收也有分配和回收成本；频繁年轻代 GC 可以出现在没有 Full GC 的情况下。
4. 代码减少分配与参数增大堆作用不同，应使用单因素对照。
5. 缓冲区复用需要线程独占或正确同步，并确保旧内容不再被消费者依赖。

基线在中午，两项对比在晚上运行，背景负载未完整记录。本轮支持优化方向，不将 19.26 倍或 1.6% 当作稳定基准。按计划三组各至少三轮的复测仍待补充，复测时保持相同配置、交替顺序、保留所有结果并记录波动。
