# 第 3 课：内存持续增长与内存泄漏

开始日期：2026-10-24。状态：学习中，已用 MAT 验证堆转储引用链，待学习者界面复现与优化验证。

学习主线见 [课程计划](../../JVM调优课程计划.md)。按“问题代码 → 观测 → 原因分析 → 优化验证”推进。本轮先收集保留量与对象数量证据，之后分析堆转储引用链，再实施优化。

## 1. 与第二课的区别

第二课的旧数组很快失去引用，可以被回收。本课模拟缓存持续保存旧数组：即使业务不再需要这些数据，只要对象仍从 GC Roots 经强引用链可达，GC 就不能按普通垃圾回收它们。

学习目标是区分临时增长、合理缓存与不合理保留：仅看到堆增长不足以判断泄漏，还要找出哪些对象增加、谁持有它们，以及业务是否仍需要它们。

## 2. 问题代码

使用 [Workloads.java](../../src/main/java/lab/Workloads.java) 中 `RetainedCache` 的 `bad` 分支。场景为接收任务后保存一份 16 KiB 数据，缓存缺少业务淘汰策略。核心逻辑等价于：

```java
private final ArrayDeque<byte[]> cache = new ArrayDeque<>();

synchronized long insert(long sequence) {
    byte[] value = new byte[16 * 1024];
    value[0] = (byte) sequence;
    value[value.length - 1] = (byte) ~sequence;
    cache.addLast(value);
    return value[0];
}
```

实际代码另有教学保护：本次缓存的数组有效载荷最多保留 64 MiB，到达上限后停止插入并设置 `capped=true`。这模拟增长阶段的保留问题，不会无限增长，也不以制造 OOM 为目标。到达平台不是业务淘汰生效，而是教学保护触发。

工作线程每轮有约 20 毫秒的等待，实际唤醒时间可能更长。本课使用一个线程放慢增长；不能预设固定吞吐或准确到达上限的秒数。

## 4. 先观察 retained 和 heap

每秒输出的两个字段含义不同：

- `retained`：程序自己记录的缓存数组有效载荷，等于缓存条目数乘以 16 KiB，不包括数组头、缓存容器及其他对象；不是堆分析器中的 retained size。
- `heap`：JVM 报告的采样时刻堆占用，包括存活对象和尚未回收的垃圾，可能因为 GC 上下波动。

观察缓存保留量是否持续上升。GC 后的堆占用可能仍较高，因为缓存中的数组仍被强引用。到达 64 MiB 后如果停止增长，结合最终 `capped` 判断是否触发保护。

## 5. 窗口 B：采集两次对象统计

设置本次实际 PID 和输出目录，程序必须仍在运行：

```powershell

& "$Jdk\bin\jcmd.exe" $JavaPid GC.class_histogram |
    Set-Content -LiteralPath "$Run\hist-before.txt" -Encoding UTF8
Get-Content -LiteralPath "$Run\hist-before.txt" -TotalCount 10
& "$Jdk\bin\jcmd.exe" $JavaPid GC.heap_info

Start-Sleep -Seconds 30

& "$Jdk\bin\jcmd.exe" $JavaPid GC.class_histogram |
    Set-Content -LiteralPath "$Run\hist-after.txt" -Encoding UTF8
Get-Content -LiteralPath "$Run\hist-after.txt" -TotalCount 10
& "$Jdk\bin\jcmd.exe" $JavaPid GC.heap_info
```

直方图按类统计对象数量和大小，重点关注类名 `[B`，它表示 `byte[]`：

```text
num     #instances         #bytes  class name (module)
...
  1:          ...            ...  [B (java.base@21.0.12.1)
```

比较两次 `[B` 的数量与字节数。统计的是整个堆的同类对象，不只这个缓存；它可以提示数组增长，但还不能独立证明所有数组由缓存持有。

`GC.class_histogram` 可能触发 GC 并造成暂停；`GC.heap_info` 是另一次采样，期间程序继续分配，两者不是同一时刻的原子快照。相关命令与影响见 [JDK 21 jcmd 文档](https://docs.oracle.com/en/java/javase/21/docs/specs/man/jcmd.html)。

如果两次统计时已经触发保护，数组数量可能不再明显增长，结合 `retained` 曲线和采样时点解释，不要求它们一定增加。

## 8. 本次实测说明了什么？

PID 16164 的同次实验中，`byte[]` 数量由 8,119 增至 9,871，总大小从约 30.872 MiB 增至 57.743 MiB；随后读取的堆 used 从约 35.967 MiB 增至 63.313 MiB。具体原始文件见 [实验记录](../../JVM调优实验记录.md)。

日志中两次对象统计触发了 Full GC，回收结果为 `33M->32M` 和 `60M->59M`，表明很多对象在回收后仍然存活。四次 GC 中包含这两次诊断触发的回收，不能按自然 GC 频率解释。

最终 `retained=64 MiB, capped=true` 是教学保护上限被触发，不是泄漏自动修复。`workerAlloc` 是整个窗口平均值，后段停止插入使平均值低于增长阶段。任务存在等待，三十多毫秒的 P99 不能直接归因于 GC。

这份直方图只能确认同类对象的数量和大小，下一步需要回答谁在持有它们。对象统计阶段尚未导出 HPROF；随后取得的转储与引用链分析见第 10 节。

## 11. 应当如何理解本次结果？

本次报告中缓存实例的 shallow heap 为 **32 字节**，retained heap 为 **20,423,104 字节，约 19.477 MiB**。后者表示该对象支配、随其不可达而可被回收的对象集合大小；不是该 Java 对象本体的大小。

其中包含 **1,245 个 16 KiB 字节数组**，数组本体总大小 20,418,000 字节。MAT 报告为约 93.91%，分母是本次分析快照的堆对象大小，不是 128 MiB 堆上限。快照在增长过程中取得，因此不是上一次最终保留 64 MiB 的那一时刻。

实际路径之一为：

```text
活动线程栈局部引用（GC Root）
  -> RetainedCache
  -> cache: ArrayDeque
  -> elements: Object[]
  -> byte[16384]
```

报告还显示 main 栈帧和 Lambda 等其他引用，不应将这一条路径当成唯一持有关系。引用链描述“谁引用谁”，与方法调用栈是不同概念。

这说明大量数组通过缓存容器保持可达。GC 无法判断业务是否还需要它们；只有结合业务生命周期，才能判断缓存是合理保留还是泄漏。MAT 自动给出的 Leak Suspects 也需要人工解释。

本轮重点是在界面中复现引用链和两类内存大小。后续再用容量边界与淘汰策略验证修复，不以 CPU 或吞吐必须提高作为成功标准。
