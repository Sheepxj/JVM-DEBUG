# 第 4 课：锁竞争与线程堆积

开始日期：2026-10-25。状态：学习中，三组首轮对比与分析已完成，复测待补充。

学习主线见 [课程计划](../../JVM调优课程计划.md)。先运行问题版，结合吞吐、CPU、线程栈与 JFR 解释时间花在哪里，再实施优化与对比验证。本例工作线程数固定，不会无限创建线程，“堆积”体现为现有线程等待；不包含外部请求队列。

## 1. 场景与问题代码

多个线程执行任务：先完成一项耗时操作，再累加共享结果。问题版将两步都放在同一个锁内。

复用 [Workloads.java](../../src/main/java/lab/Workloads.java) 的 `LockContention` 场景。问题分支等价于：

```java
private final Object gate = new Object();
private long sharedTotal;

long execute(long sequence) {
    synchronized (gate) {
        simulatedSlowOperation();
        sharedTotal += sequence;
    }
    return sequence;
}

private static void simulatedSlowOperation() {
    LockSupport.parkNanos(4_000_000);
}
```

所有工作线程共享同一 `gate`。`parkNanos` 用等待模拟慢操作，不执行真实磁盘或网络 I/O；4 毫秒是请求的等待时长，实际唤醒、调度和锁排队可能更长。

本课先观察同步块、线程状态和等待关系，不先阅读 `fixed` 分支。业务假设是慢操作本身不访问受 `gate` 保护的共享状态；后续修改锁范围前仍需检查这一前提。

## 2. 本轮要收集的证据

1. CPU 忙不忙，吞吐和 P99 是多少？
2. 四个 `lab-worker-*` 分别在执行、等待锁，还是等待唤醒？
3. 等待者是否指向同一把锁，能否找到持有者？
4. 一段时间内，哪些代码位置记录到较多或较长的锁竞争？

不能只凭 CPU 低判断程序状态良好，也不能只凭一次线程等待判断死锁。

## 4. 窗口 B：采集三次线程栈

使用窗口 A 的实际进程号和输出目录，确保程序仍然运行：

```powershell
$Jdk = 'J:\JDK\jdk_21\temurin-21.0.12.1'
$JavaPid = 12345  # 替换为本次实际 PID
$Run = '这里替换为本次 Artifacts 完整路径'

& "$Jdk\bin\jcmd.exe" $JavaPid Thread.print -l |
    Set-Content -LiteralPath "$Run\threads-1.txt" -Encoding UTF8
Start-Sleep -Seconds 2
& "$Jdk\bin\jcmd.exe" $JavaPid Thread.print -l |
    Set-Content -LiteralPath "$Run\threads-2.txt" -Encoding UTF8
Start-Sleep -Seconds 2
& "$Jdk\bin\jcmd.exe" $JavaPid Thread.print -l |
    Set-Content -LiteralPath "$Run\threads-3.txt" -Encoding UTF8

Select-String -LiteralPath "$Run\threads-1.txt" -Pattern '"lab-worker-' -Context 0,12
```

其他两份按相同方式查看。线程栈命令说明见 [JDK 21 jcmd 文档](https://docs.oracle.com/en/java/javase/21/docs/specs/man/jcmd.html)。

重点识别以下组合，实际线程号与地址以本次输出为准：

```text
等待者：
  java.lang.Thread.State: BLOCKED (on object monitor)
  - waiting to lock <0x...> (a java.lang.Object)

持有者：
  java.lang.Thread.State: TIMED_WAITING (parking)
  at ...LockSupport.parkNanos(...)
  at ...simulatedSlowOperation(...)
  - locked <0x...> (a java.lang.Object)
```

在同一份线程快照中，将多个 `waiting to lock` 的对象地址与持有者的 `locked` 地址对应，确认是否是同一个监视器。线程池 Worker 也可能出现在同步器列表中，本课重点是源码中 `gate` 对应的对象。

`BLOCKED` 在这里指等待进入 `synchronized` 监视器；持有者可能处于 `TIMED_WAITING`，因为它在同步块中调用 `parkNanos`，并没有因此释放已经持有的监视器。这两种等待的原因不同。线程状态见 [官方定义](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/lang/Thread.State.html)。

锁竞争不等于死锁；需要结合多次快照和持续完成量判断是否仍在前进，死锁还需要分析循环等待关系。也不要把 `ReentrantLock` 等其他锁的等待状态都认定为 `BLOCKED`。

## 5. 程序结束后，查看 JFR 锁竞争

在已设置 `$Jdk`、`$Run` 的窗口 B 中执行：

```powershell
& "$Jdk\bin\jfr.exe" view --width 120 contention-by-site "$Run\recording.jfr"
```

主要关注业务代码位置 `Workloads$LockContention` 的 `Count`、`Avg.`、`Max.`，查看哪些位置有竞争等待。该视图不是每次任务延迟的完整分布，平均等待不能直接当作业务 P99。

需要查看具体事件时导出：

```powershell
& "$Jdk\bin\jfr.exe" print --events jdk.JavaMonitorEnter --stack-depth 15 "$Run\recording.jfr" |
    Set-Content -LiteralPath "$Run\monitor-events.txt" -Encoding UTF8
```

`jdk.JavaMonitorEnter` 可提供事件线程、竞争进入监视器的耗时、监视器类型、先前持有者和调用栈等信息。关注 `duration`、`eventThread`、`previousOwner` 和业务栈；`duration` 是竞争进入的等待，不是持有锁的时间。启动阶段还会有类加载、JFR 自身等事件，不能全部归为业务锁。

阈值之外的短事件或未竞争的进入不会都出现在结果中；未记录到事件不等于完全没有同步。不同线程的等待可同时发生，不能把等待时间之和当作单个进程的墙钟停顿。JFR 覆盖启动和预热，而 `RESULT` 只汇总测量阶段，统计窗口也不同。

命令参考 [JDK 21 jfr 官方文档](https://docs.oracle.com/en/java/javase/21/docs/specs/man/jfr.html)。

## 7. 本次实测与原因分析

学习者四线程问题版吞吐约 64.118 任务/秒，P99 约 171.966 毫秒，平均进程 CPU 核数 0.017426。按当前 12 个可见逻辑处理器粗略归一化约为整机 0.145%，所以任务管理器显示接近 0 并不矛盾。

工作线程 1、2、3 等待 `<0x00000000fff72630>`；工作线程 4 在 `parkNanos` 中，同时仍持有该监视器。JFR 业务位置有 3,411 个竞争事件，平均等待 57.0 毫秒、最大 340 毫秒。详细证据见 [实验记录](../../JVM调优实验记录.md)。

问题代码把耗时等待包在同一锁中，使其他线程无法独立执行这一步；CPU 大多闲置，业务仍因排队变慢。任务持续完成，不能将这种竞争直接认定为死锁。

4 毫秒是请求等待时长，实际调度与锁排队都能延长任务耗时；也不能将 JFR 单类事件的平均等待与业务 P99 相等看待。

## 8. 缩小临界区，保留必要同步

现有 fixed 分支的核心逻辑：

```java
simulatedSlowOperation();
synchronized (gate) {
    sharedTotal += sequence;
}
```

慢操作自身不依赖共享状态，可以移到锁外；共享累加仍然受锁保护。不要直接删除同步，也不能把字段换成 volatile 就认为累加已经原子化。

真实业务中先检查慢操作与共享状态的依赖、原子性和顺序要求，再决定能否缩小锁范围。

## 9. 两项对比实验

在同一个 PowerShell 按顺序执行，分别与已有四线程 bad 基线比较：

```powershell

# 保持问题代码，只将线程数改为 1。

```

第一项检验缩小锁范围的收益，第二项检验增加线程是否带来容量提升。不要把 fixed/4 与 bad/1 之间的差异当作单因素结果。

保留两次 RESULT、输出目录，方便时分别读取 JFR 的 `contention-by-site`。预期 fixed 的竞争减少；若事件为零，结合 1 毫秒阈值理解，不代表取消了锁。bad/1 即使延迟降低，也要同时看总吞吐，不能只看没有排队就认定容量提高。

## 11. 减少排队与提升容量的区别

- **bad/4**：一个线程持锁执行慢操作，其他线程排队，吞吐低且内部任务耗时较长。
- **bad/1**：没有工作线程之间的业务锁竞争，减少内部排队，但任务仍逐项执行，容量没有显示出明显提高。
- **fixed/4**：四个独立慢操作可同时进行，共享累加短暂加锁；单项耗时接近慢操作本身，同时完成量增加。

因此相近的 P99 可以对应不同吞吐，不能只凭延迟降低就认定容量提高。闭环负载没有模拟外部请求队列，减少线程可能只是把真实系统的等待转移到别处。

两个对比的 JFR 没有记录到该业务位置达到阈值的竞争，但同步仍存在。P95/P99 显示相同还受直方图分桶影响，并不表示每次耗时一样。

## 12. 面试复习与进度

本课应掌握：

1. CPU 低、GC 不频繁，仍可能因锁内慢操作而吞吐低、延迟高。

3. 区分 BLOCKED 的监视器竞争与持锁线程自身的限时等待，不将锁竞争直接当作死锁。
4. 缩小临界区之前检查共享状态、原子性和顺序要求，保留必要同步。
5. 同时比较吞吐和延迟，理解增加线程、减少排队与容量提升的差别。
