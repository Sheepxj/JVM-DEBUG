# 第 6 课：独立完成一次调优

开始日期：2026-10-25。更新日期：2026-10-26。状态：学习中，三阶段首轮排查与逐项优化闭环已完成，多轮复测待补充。

本课按 [课程计划](../../JVM调优课程计划.md) 进行：包含两类已学问题，开始时不揭示位置。学习者先选择指标与工具、提出假设，再根据实际证据决定优化顺序，每次验证一项改动。

## 1. 场景与业务约束

一个报表任务根据输入生成计算结果，再处理报表内容并返回摘要。所有步骤在当前任务内完成，数据不交给异步消费者；本实验在内存中模拟工作，不连接数据库、网络或真实文件存储。

代码已接入现有实验框架，场景名为 `report`。源代码位于 [Workloads.java](../../src/main/java/lab/Workloads.java)。先以运行证据确定要读的代码位置，暂不阅读 `fixed` 分支。观察到的方法名属于定位线索，不应单凭名称判断根因。

业务正确性要求：相同输入返回相同摘要；保持各任务彼此独立、必要的线程安全与数据生命周期。后续优化前，应结合代码核对输入范围、结果有效期和数据所有权。

本课要练习完整流程：业务表现 → 指标分类 → 诊断证据 → 对应源码 → 优化假设 → 单项改动 → 对比验证 → 检查新瓶颈。

## 2. 当前程序与实验边界

- 使用之前确认的 Temurin 21.0.12.1+1、G1、128 MiB 固定堆、4 个平台工作线程。
- 5 秒预热、120 秒测量，给现场诊断留出时间；采用脚本现有 GC 日志和 JFR profile，后续对比保持相同配置。
- 这是固定并发闭环：完成一项任务后开始下一项，没有外部请求队列。吞吐与 P99 是内部任务指标。
- `retained` 是已有缓存场景的有效载荷计数；本场景不使用该计数来量测所有存活对象，不把其零值当作没有存活对象的证据。
- `bad` 为起点；完整改进分支虽可用于正确性自检，本课按证据逐项实施修改，暂不直接运行 `fixed` 跳过中间验证。

## 3. 启动正式问题版

在项目根目录 PowerShell 执行：


## 5. 定位后的优化与验证

先把证据对应到具体代码，说明业务前提，再选择第一处改动。中间版本在选定方案后准备并记录：只改变一个因素，保留另一处行为，验证业务结果及指标；不提前固定必须先优化哪一类问题。

保持 JDK、负载、线程、堆、预热、时长与录制配置一致。`report` 每轮会在运行目录的 `source/` 保存 Java 主程序源码，`run.json` 记录快照位置；模式名与源码快照共同关联中间版本和对应结果，必要时可根据快照生成差异补丁。第二项改动与第一项改动后的版本比较，并再次观察热点是否转移。

正式结论每组至少三轮，记录背景负载与波动。对参数试验同样一次只改一项，不把增大堆和改代码合成一次验证。

## 7. 正式基线与下一步（2026-10-25）

本轮目录 `artifacts/20261025-201724-019-report-bad-78fdca`，配置与第 3 节一致。吞吐 32,863.049/s，P99 1.146880 ms，每任务分配 262,272 字节，工作线程分配约 8.027 GiB/s；测量期 GC 13,578 次，约 113.13 次/秒。用户提供的 Young GC 样例为 `79M->4M(128M)`，支持大量短命对象的假设。

CPU 约整机 30% 对应本机约 3.6 个核，结合 4 个工作线程不能直接排除计算热点。JFR summary 按事件数或编码大小排序不表示 CPU 时间排序，GCPhaseParallel 的子阶段事件数也不等于 GC 次数。

下一步离线分析两项视图，不必重新启动进程：

```powershell
$Jdk = 'J:\JDK\jdk_21\temurin-21.0.12.1'
$Run = 'D:\Files\Documents\ChatGPT\JVM调优学习\artifacts\20261025-201724-019-report-bad-78fdca'

& "$Jdk\bin\jfr.exe" view --width 120 allocation-by-site "$Run\recording.jfr"
& "$Jdk\bin\jfr.exe" view --width 120 hot-methods "$Run\recording.jfr"
```

第一项查看哪些位置贡献主要分配压力，第二项查看哪些 Java 方法出现较多执行采样；采样占比不是精确 CPU 时间占比。结合两项输出提出源码检查与第一项优化顺序，暂不直接套用完整 fixed。

该 JFR 因 64 MiB 近似保留预算，只保留后半段约 62 秒，具体窗口由 summary 的 Start/Duration 确认；不能与完整测量期汇总当作相同时间窗。当前记录足以继续查看热点，后续保持相同录制配置并检查覆盖范围。命令说明见 [JFR 官方文档](https://docs.oracle.com/en/java/javase/21/docs/specs/man/jfr.html)，实际基线与统计限制见 [实验记录](../../JVM调优实验记录.md)。

## 8. 两项定位结果与优化选择

学习者已反馈：

| 观察 | 主要位置 | 当前含义 |
|---|---|---|
| 分配压力显示 100.00% | AllocationWorker.execute | 主要临时对象创建位置，百分比受采样与显示精度影响 |
| 执行采样 2,981 个、90.58% | Cpu.expensiveScore | 主要 Java 执行热点，不是全进程精确 CPU 时间比例 |

两处对应源码均可在 Workloads.java 查看。计算分支的输入范围、结果稳定性，以及缓冲区分支的数据所有权，是提出优化前要核对的业务前提。

定位后建议优先验证主要 Java 执行热点；也可以先减少分配，只要保留另一项行为并逐项比较。随后学习者提出了数组复用与预计算两项方案，现按先前建议准备只优化计算的中间版本，见下一节，不按采样占比承诺收益。

## 9. 第一步：只优化重复计算（2026-10-26）

学习者提出：复用数组减少分配；提前计算结果，后续直接读取。这两个方向适用于本实验，需明确以下前提：

- 缓冲区由每个工作线程独立持有，当前处理结束后没有外部或异步消费者继续使用旧内容，才可以覆盖复用；四个线程不共用一块可变数组。
- 计算输入只有 0～255，且同一 key 的结果稳定。初始化时算好 256 项，完成初始化后供工作线程只读查询，不能将此方案直接套到任意动态输入或随时间变化的业务规则。

已将报表的两项行为拆开选择，提供三个阶段，旧场景行为保持原样：

| report 模式 | 计算 | 数组 |
|---|---|---|
| bad | 每任务重新计算 | 每任务新建 |
| cpu-fixed | 初始化预计算，任务内查表 | 每任务新建 |
| fixed | 初始化预计算，任务内查表 | 每工作线程复用 |

第一轮只从 bad 到 cpu-fixed，不修改堆或暂停目标：

```powershell
Set-Location 'D:\Files\Documents\ChatGPT\JVM调优学习'
$Jdk = 'J:\JDK\jdk_21\temurin-21.0.12.1'
.\scripts\run.ps1 -JdkHome $Jdk -Scenario report -Mode cpu-fixed -Threads 4 -HeapMiB 128 -WarmupSeconds 5 -Seconds 120 -Collector G1 -Recording
```

`cpu-fixed` 仅对 report 开放。构造报表时启用 Cpu 的已有预计算分支，Allocation 保持问题分支；原有 bad 和 fixed 的业务行为不变。初始化计算发生在工作线程计时前，不能把初始化成本当作消失，需按应用运行时长和启动要求评估。

完成后反馈 RESULT、新运行目录和 hot-methods。核对 summary.csv 的每任务分配量应仍约 262,272 字节；分配与 GC 仍可能频繁，每秒分配量也可能随吞吐增加。执行热点应发生变化，但 JFR 含启动阶段时不要求 expensiveScore 样本严格为零。实际收益与新瓶颈以正式输出为准。

当前基线是 2026-10-25 的 120 秒运行，跨日比较仅作首轮线索；稳定收益需要将新旧版本按相同条件交替复测。随后收到的本课中间版本正式结果如下。

## 10. 第一步实测：计算热点消退，整体收益有限

本轮目录 `artifacts/20261026-110936-036-report-cpu-fixed-336507`，配置已核对符合第 9 节。

- 吞吐 34,540.054/s，比原基线高约 5.1%；P99 1.245184 ms，比原基线高约 8.6%，不能声称业务尾延迟改善。
- 每任务分配仍为 262,272 字节；测量期 GC 14,270 次，累计统计时间 13,674 ms。每秒分配和 GC 总数的增加与任务量增长有关，两组每千任务 GC 均约 3.44 次。
- hot-methods 首位转为 AllocationWorker.execute，827 个样本、93.76%；保留窗口内未显示 expensiveScore。allocation-by-site 中主要分配位置不变。
- 当前 JFR 只保留后半段约 66 秒，不以此宣称初始化阶段没有预计算调用。

这一轮体现了消除一个热点后需要重新观测。Java 执行采样占比不等于全部耗时比例，原来 90.58% 的热点消退不能直接换算成吞吐收益。数组方法包含分配、填充与读写，其样本也不能全算作 GC 时间；剩余 GC 与高分配仍需处理。跨日、单轮数据只提供线索。

## 11. 第二步：只在中间版本基础上增加数组复用

`cpu-fixed` 与 `fixed` 都已启用预计算，二者只在数组是否复用上不同。运行：

```powershell
$Jdk = 'J:\JDK\jdk_21\temurin-21.0.12.1'
.\scripts\run.ps1 -JdkHome $Jdk -Scenario report -Mode fixed -Threads 4 -HeapMiB 128 -WarmupSeconds 5 -Seconds 120 -Collector G1 -Recording
```

每个工作线程独立持有一块 32 KiB 缓冲区，任务内 8 次处理都覆盖填充并消费结果，再复用同一块空间；没有跨任务异步消费者，所以无需为旧内容额外保留数组。计算、内容处理与校验仍执行，结果不是直接从报表结果缓存返回。

与 cpu-fixed 比较时，重点核对每任务分配是否显著下降、GC、吞吐、P99 与 hot-methods。初始化仍有数组分配，统计近零不代表 JVM 从启动起没有分配；消除分配也不意味着数组填充的工作消失。随后收到的 fixed 正式结果如下。

## 12. 第二步实测与三阶段结论（2026-10-26）

fixed 目录 `artifacts/20261026-113536-859-report-fixed-440e36`，配置和代码快照已核对。

| 指标 | bad | cpu-fixed | fixed |
|---|---:|---:|---:|
| 吞吐（任务/秒） | 32,863.049 | 34,540.054 | 724,434.244 |
| P99（微秒） | 1,146.880 | 1,245.184 | 8.704 |
| 每任务分配（字节） | 262,272.000 | 262,272.000 | 0.000 |
| 测量期 GC 次数 | 13,578 | 14,270 | 0 |

新增数组复用后，本轮吞吐相对中间版本约 20.97 倍、P99 降低约 99.3%；完整两项优化相对原版吞吐约 22.04 倍。分配统计在显示精度下近零，不代表初始化及全 JVM 没有分配。

完整日志仅在 uptime 0.839 秒记录一次启动期 Young GC；测量期无 GC。JFR 本轮保留约 125 秒，首位 Java 热点为 Arrays.fill，占执行样本 91.48%，表明内容填充仍执行。三组录制覆盖范围不同，不直接比较事件总数。

CPU 核数从中间版本的 3.347 增至 3.929，同时完成任务数显著增加，不能凭 CPU 升高判断优化失败。热点集中到必要业务处理后，是否继续优化应由业务目标决定。
